# Storage Schema Overview

This document describes the current schema definitions and data-access code. PostgreSQL has three tables; Redis structures are grouped separately. `PK` means primary key, including an implicit non-null constraint and unique index. Fields without DEFAULT have no explicitly declared database default.

## Session Messages (PostgreSQL)

### `session_message`

One row per persisted chat message. Stores the session identity, the complete versioned message document, including assistant tool_calls and tool tool_call_id, and its creation time, providing durable history when the Redis cache is empty. Task messages are never written here.

| Field | Type | Constraints | Description |
| --- | --- | --- | --- |
| `message_id` | `UUID` | PK | UUID v4 generated by the application when writing the message |
| `create_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT `NOW()` | Message creation time; the actual field name is `create_at` |
| `session_id` | `TEXT` | NOT NULL | Session identifier, without a foreign key to a session master table |
| `sequence_no` | `BIGINT` | Generated sequence, ordered index with session_id | Stable append ordering; migration backfills legacy history in its old read order |
| `content` | `JSONB` | NOT NULL, JSON object check | Complete `MessageItem` document, including version, role, and typed content parts |

Constraints and indexes:

- `INDEX idx_session_message_history (session_id, create_at, message_id)` supports deterministic history queries by session and time.
- `session_id` has no foreign key; no session master table exists. Message structure is validated by the application model.
- Chat messages are written to PostgreSQL first, then Redis. Task messages and their image references live in the service process.
- On a chat cache miss, history is loaded in `sequence_no` order and copied into Redis.
- Chat expiration clears cached messages and retains chat metadata and PostgreSQL history. Task expiration releases the in-memory messages and deletes their Redis image keys. Explicit deletion removes all storage owned by either type.

## Model Service Resources (PostgreSQL)

### `openai_resource`

One row per OpenAI-compatible model service configuration, storing connection settings, enabled status, selection priority, and soft-deletion time.

| Field | Type | Constraints | Description |
| --- | --- | --- | --- |
| `resource_id` | `TEXT` | PK | UUID v4 string generated by the creation method |
| `model` | `TEXT` | NOT NULL | Model name |
| `api_key` | `TEXT` | NOT NULL | API key; the current accessor reads and writes it as text |
| `base_url` | `TEXT` | NOT NULL | OpenAI-compatible service URL |
| `bypass_proxy` | `BOOLEAN` | NOT NULL, DEFAULT `FALSE` | When true, connect directly without environment proxies for this provider |
| `deleted_at` | `TIMESTAMPTZ` | NULL | Soft-deletion time; NULL for records that have not been deleted |
| `enabled` | `BOOLEAN` | NOT NULL, DEFAULT `TRUE` | Whether the resource participates in selection |
| `priority` | `INTEGER` | NOT NULL, DEFAULT `0` | Higher values take precedence |

Constraints and indexes:

- `CHECK (deleted_at IS NULL OR enabled = FALSE)`, named `openai_resource_deleted_disabled`, prevents a soft-deleted resource from being enabled.
- `INDEX idx_openai_resource_enabled (enabled, priority DESC)`.
- Proxy bypass applies when a session creates its model client. Existing sessions retain their client settings; private IP and localhost endpoints continue to bypass proxies automatically.
- Model names and service URLs have no unique constraint. `priority` has no non-negative constraint.
- Selection filters by `enabled = TRUE AND deleted_at IS NULL`, sorts by `priority DESC, resource_id`, and takes the first row.
- Soft deletion sets `deleted_at = COALESCE(deleted_at, NOW())` and `enabled = FALSE`, retaining the record and its original deletion time.

## Session Cache (Redis)

### `chat:{session_id}:messages`

One List per cached chat. Each element is a JSON message from the persisted history.

| Field | Type | Constraints | Description |
| --- | --- | --- | --- |
| `role` | `str` | Required by the application model | Message role |
| `content` | `str` | Required by the application model | Message content |

Constraints and indexes:

- Append with `RPUSH` and read with `LRANGE 0 -1`. There are no relational primary keys, foreign keys, or secondary indexes.
- New list entries include message_id and optional tool_calls/tool_call_id; legacy entries remain readable.
- Writes set no TTL. Chat expiration removes the cache while retaining PostgreSQL messages.

### `chat:{session_id}:meta`

One String per chat containing a JSON `SessionMeta` document. It records the session ID, type, setting, reconnect window, creation time, and disconnect time. It prevents a session ID from changing storage policy while metadata exists.

### `task:{session_id}:image:{media_id}`

One Redis String per uploaded image. The task message list lives in process memory.

| Field | Type | Description |
| --- | --- | --- |
| `session_id` | String | Identifies the owning task in the Redis key. |
| `media_id` | UUID v4 | Generated at upload and used as the final segment of the key. |
| `image_path` | String | Full Redis key stored in the in-memory message’s image part. |
| Redis value | Binary string | Original image bytes. DA reads them with `GET image_path` and base64-encodes them when building model input. |

- Upload sets the value and its expiry in one `SET ... EX` operation. The TTL is `max(300, reconnect_keep + 60)` seconds.
- The service refreshes image TTLs about once a minute while the session is retained. Expiry or explicit session deletion removes the keys.
- After a service restart, task history is lost and any remaining image keys expire automatically.

Invocation logs are stored in files. The client has no independent database tables.


## Conversation memory

`session_memory_checkpoint` stores `id UUID PRIMARY KEY`, `session_id TEXT NOT NULL`,
`summary TEXT NOT NULL`, `compacted TEXT NOT NULL`, `last_message_id UUID NOT NULL`,
and `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`. Both text fields must be nonempty.
The unique `(session_id, last_message_id)` makes repeated saves idempotent; its composite
foreign key references `session_message(session_id, message_id)` with ON DELETE CASCADE.

The boundary is the generated compacted **user message**, inclusive. Restored model
context contains the current system prompt, the newest compacted user message, and
subsequent messages. Original PostgreSQL messages remain stored. Ordinary tool calls
and results persist across chat triggers.

Chat clients register MemoryOperator with compact(), list(), and check(checkpoint_id).
compact() has no arguments: a separate compact task agent generates summary and
compacted detail using its output operator. A hard limit invokes this compaction
path directly; it does not force the main agent to choose a tool. User compact
settings are appended to the default compact prompt. Task clients do not register
the memory operator. Task sessions keep no memory checkpoints.

Existing installations use migrations/memory_history.sql; fresh installations use
python -m dynamic_agent_service.init_storage. On 2026-11-17 the existing migration
was applied to the live public schema in dynamic_agent_service. All 723 pre-existing
message rows were verified unchanged; sequence_no was backfilled and the separate
session_memory_checkpoint table created. The table_wiki_lab schema is isolated
experiment storage and is not the downstream service's default schema.

Defaults are 512,000 / 768,000 tokens. Latest reported usage plus an approximate
pre-call message-size check controls the soft prompt and direct hard-limit
compaction. The estimate is not an exact tokenizer.

Run the isolated real-model smoke test with `python tests/smoke/memory.py` from the DA
root using its environment. It uses limits 1,600 / 2,400, a unique session, an ephemeral
HTTP port, and a temporary PostgreSQL schema. It cleans up its test storage and writes
`cache/memory-smoke.json`. It requires the configured model, PostgreSQL and Redis.
